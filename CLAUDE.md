# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Native macOS app (Swift 6 / SwiftUI, deployment target macOS 15) that records a chosen window's video plus two **separate** audio streams — the user's mic and the meeting app's process-level output — then runs WhisperKit + SpeakerKit locally on the result to produce a speaker-labelled transcript. The point of capturing per-process output audio (rather than the whole desktop mix) is so that diarization can split meeting participants without picking up Spotify, notifications, etc.

## Build and test

The Xcode project is generated by **XcodeGen** from `project.yml`. Never hand-edit `Meeting.xcodeproj`; it gets regenerated.

```bash
# After adding or moving Swift files, or after editing project.yml:
xcodegen generate

# Build (no signing — for compile checks only):
xcodebuild -project Meeting.xcodeproj -scheme Meeting -configuration Debug \
  -destination 'platform=macOS' \
  CODE_SIGN_IDENTITY=- CODE_SIGNING_REQUIRED=NO CODE_SIGNING_ALLOWED=NO build

# Build with stable Personal-Team signing (matches what Xcode does — required
# for the running app to keep TCC permissions across rebuilds):
xcodebuild -project Meeting.xcodeproj -scheme Meeting -configuration Debug \
  -destination 'platform=macOS' build

# Run all tests:
xcodebuild -project Meeting.xcodeproj -scheme Meeting -configuration Debug \
  -destination 'platform=macOS' test

# Run a single test:
xcodebuild -project Meeting.xcodeproj -scheme Meeting -destination 'platform=macOS' \
  -only-testing:MeetingTests/TranscriptMergerTests/test_mergedSegments_areSortedByStartTime test
```

`Info.plist` and `Meeting.entitlements` are **generated** from `project.yml` (gitignored). Edit `project.yml` to change usage descriptions, entitlements, or signing.

## Code signing and TCC

Stable signing is critical: macOS TCC keys "Allowed apps" by code signature, so ad-hoc signing (`CODE_SIGN_IDENTITY=-`) re-prompts for Screen Recording / Microphone / Audio Capture every rebuild. `project.yml` hardcodes `DEVELOPMENT_TEAM: 49AUFL5Q3U` (Personal Team for `fluke.s@finnomena.com`); switching teams or building unsigned will require re-granting permissions and `tccutil reset All dev.fluke.meeting`.

## High-level architecture

Three layers, each in its own folder under `Meeting/`:

### `Meeting/Capture/` — recording pipeline

`RecordingSession` (@MainActor) is the orchestrator. On `start(window:)` it spins up three independent capture pipelines and on `stop()` tears them down in the right order so each file's trailer flushes:

- **`ScreenCaptureCoordinator`** — `SCStream` with a window-only `SCContentFilter` plus `SCRecordingOutput` writing `video.mov`. Includes a no-op `SCStreamOutput` (`FrameSink`) purely to silence "stream output NOT found, dropping frame" log spam that SCStream emits when no consumer is attached.
- **`MicRecorder`** — `AVAudioEngine` input tap → `AVAudioFile` writing `mic.wav` as 16-bit interleaved PCM. Intentionally **not `@MainActor`** (see "Audio thread isolation" below).
- **`ProcessAudioTap`** — Core Audio Tap (`CATapDescription` + private aggregate device + `AudioDeviceCreateIOProcIDWithBlock`) writing `output.wav`. This is the only API that captures a single app's audio without picking up the rest of the system.

Files land at `~/Documents/Meetings/<yyyy-MM-dd_HH-mm-ss>/`. Folder names auto-suffix `-2`, `-3`, etc., on collisions.

### `Meeting/Transcribe/` — transcription pipeline

`TranscriptionProvider` (Sendable protocol) is the abstraction. After `RecordingSession` finishes, `RecordingMainView` invokes `TranscriptionSession.run(meetingFolder:expectedSpeakers:)` which:

1. Calls the provider on `mic.wav` with `knownSpeaker: .me` (no diarization).
2. Calls the provider on `output.wav` with `withDiarization: true`.
3. Merges via `TranscriptMerger.merge(mic:output:)` into a single chronological timeline; "Me" sorts first, then `speaker_0`, `speaker_1`, …
4. Writes `transcript.json`, `transcript.md`, and `transcript.srt` next to the audio via `TranscriptExporter`.

`LocalProvider` (the only implementation right now) is an `actor` that single-flights WhisperKit + SpeakerKit model loads. It runs WhisperKit (default `large-v3`, **not** `_turbo` — turbo's auto-language-detect misclassifies Thai content as English) with `wordTimestamps: true` and `chunkingStrategy: .vad`, then for `output.wav` also runs SpeakerKit with `clusterDistanceThreshold: 0.7` (pyannote's default 0.6 over-splits single-speaker recordings) and stitches the two via `addSpeakerInfo(strategy: .subsegment)`. The output language is forced to `"th"` in `TranscriptionSession` to keep Thai-English code-switching content from being decoded entirely in English.

`HallucinationFilter` drops the boilerplate Whisper emits on silent chunks ("you", "Thank you.", "Subscribe.", music note glyphs) when the duration is short enough that they're plausibly a misfire.

`ModelStorage.downloadBase()` returns `~/Library/Application Support/dev.fluke.meeting/Models/` and is passed to both `WhisperKitConfig.downloadBase` and `PyannoteConfig.modelDownloadConfig.downloadBase`. Without this override the kits dump multi-GB CoreML weights into `~/Documents/huggingface/`, which iCloud sync ingests.

### `Meeting/App/` — shell, permissions, preferences

`MeetingApp` (`@main`) hosts a single `WindowGroup` containing `ContentView`, which routes to either `PermissionView` or `RecordingMainView` based on `AppState.permissions`. `PermissionManager` checks/requests the three TCC services using `CGPreflightScreenCaptureAccess`, `AVCaptureDevice.requestAccess`, and a `CATapDescription(stereoGlobalTapButExcludeProcesses: [])` probe (note: the **global** tap variant, because the empty-mixdown variant returns `kAudioUnitErr_InvalidElement` and never triggers the TCC prompt). `AppPreferences` persists user settings (currently just `expectedSpeakerCount` for diarization) via `UserDefaults`.

## Project-specific gotchas

These are non-obvious things that have already cost us debugging time — preserve them:

### Audio-thread closure isolation (Swift 6 strict concurrency)

`AVAudioNode.installTap`, `AudioDeviceCreateIOProcIDWithBlock`, and other audio-render callbacks are typed as non-`@Sendable` closures. If the enclosing class is `@MainActor`, the closure inherits MainActor isolation and traps in `_dispatch_assert_queue_fail` (`EXC_BREAKPOINT`) the moment the audio thread fires it. **`MicRecorder` and `ProcessAudioTap` are deliberately not `@MainActor`** and are marked `@unchecked Sendable`. Audio resources (e.g. `AVAudioFile`) are wrapped in `@unchecked Sendable` boxes (`AudioFileBox`) so the closure can capture them without dragging in actor isolation.

### Sendable boxes for WhisperKit / SpeakerKit

Both kits are non-final open classes that the compiler refuses to mark `Sendable`. `LocalProvider` wraps them in `KitBox` / `DiarizerBox` (`@unchecked Sendable`) so model handles can return from a `Task<KitBox, Error>` for single-flight loading and cross actor boundaries safely. Real cross-actor calls (`box.kit.transcribe(...)`) happen in `nonisolated static` helper methods that take the box as a parameter.

### Electron apps need multi-process taps

Discord, Slack, Teams, VS Code Live Share — Chromium-based apps put VoIP/media in helper processes whose PIDs differ from `SCWindow.owningApplication.processID`. Tapping only the main PID returns a tap that never delivers IOProc callbacks. `ProcessAudioTap.collectAudioObjectIDs` enumerates `kAudioHardwarePropertyProcessObjectList`, includes every audio process whose `kAudioProcessPropertyBundleID` equals the target's bundle ID or starts with `<bundleID>.`, and passes the union to `CATapDescription(stereoMixdownOfProcesses:)`. Verified against Discord on 2026-04-29: 4 audio processes (`com.hnc.Discord`, `.helper`, `.helper.Renderer`, `.helper.Plugin`) → 1.16 M frames captured.

### `List(selection:)` and SwiftUI publish warnings

macOS's `List` writes the selection binding synchronously inside the click event, mid-render. If the binding is on an `@Published` property, this triggers "Publishing changes from within view updates is not allowed". `WindowPicker.deferredSelection` wraps the binding so the write is deferred via `DispatchQueue.main.async`. Apply the same pattern to any new `List(selection:)` bound to `@Published` state.

### XcodeGen pitfalls

- New `.swift` files are picked up automatically — but the project must be re-generated (`xcodegen generate`) before `xcodebuild` will find them.
- `Info.plist` keys live under `targets.Meeting.info.properties` in `project.yml`. `GENERATE_INFOPLIST_FILE` is `NO` for the app target; XcodeGen writes the plist itself.
- `MeetingTests` target uses `GENERATE_INFOPLIST_FILE: YES` (Xcode generates a stub).

## Optional sidecar: `tools/typhoon/`

A Python venv with `typhoon-asr` (NeMo / FastConformer-Transducer, Thai-only model from SCB10X) plus a chunked wrapper at `tools/typhoon/transcribe.py` lives outside the app bundle. It's not currently wired into the Swift code — it was used for benchmarking against WhisperKit and is kept as a future provider option for Thai-only meetings. The venv (~1.7 GB) is gitignored. Bring it back with `tools/typhoon/setup.sh` (requires `python3.11` from Homebrew) if you want to invoke it as a `TranscriptionProvider` via subprocess.
